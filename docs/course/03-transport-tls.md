# 03｜TCP、UDP、HTTP、HTTPS 与 TLS

**本课目标**：理解“连接成功”和“内容安全”是两回事，明白 VPN/代理为什么有多种传输方式。

## 先分清三层职责

想象给朋友寄快递：

- **IP**：把包裹朝目的地址转发，尽力而为，不承诺一定送达。
- **TCP / UDP**：确定程序之间怎样发送数据。TCP 提供面向连接、按序、可靠的字节流；UDP 是无连接的数据报，不内建可靠重传机制。
- **HTTP**：定义浏览器与网站如何表达请求与响应；**TLS**：为通信建立加密、完整性保护及服务端身份验证。

“UDP 不可靠”不是“基于 UDP 的应用一定丢数据”；QUIC 在 UDP 上自己实现了可靠传输与拥塞控制，HTTP/3 就基于 QUIC。

## 为什么 HTTPS 不只是加密？

浏览器先使用 TLS 验证网站证书是否可信、域名是否匹配、证书是否有效，再建立加密通道。一个正确配置的普通网络代理可以看见连接相关的元信息，但**不能仅凭转发 HTTPS 流量就读懂网页正文**。如果设备安装了不可信的根证书、被恶意软件控制或网站本身不安全，则另当别论。

HTTPS 不等于完全匿名。对端 IP、连接时间、流量大小等信息仍可能被网络路径上的参与者观察；某些域名相关元数据是否可见，还取决于 DNS、TLS/ECH、代理部署与具体协议。

## 一次 HTTPS 请求的简化过程

```text
DNS（可能）→ 选路由
→ TCP 三次握手（若使用 HTTP/2 over TCP）
→ TLS 握手：验证证书并协商密钥
→ 加密发送 HTTP 请求
→ 加密收到 HTTP 响应
```

使用 HTTP/3 时，QUIC 运行在 UDP 上，细节会不同。学习阶段先以 HTTP/2/TCP 这个常见模型理解即可。

## 端口与监听

Linux 服务器上：

```bash
sudo ss -lntup
```

解释：`LISTEN` 表示 TCP 程序正在等待连接；UDP 通常没有相同意义的 LISTEN 状态。`0.0.0.0:22` 表示监听全部 IPv4 接口上的 22 端口，而 `127.0.0.1:1080` 只接受同一台机器发起的 IPv4 本地连接。

Windows 本机：

```powershell
netstat -ano
```

注意：**有进程监听不代表防火墙或云平台已经放行**；反过来，放行端口也不会凭空创建监听程序。

## 常见误区

- “TCP 比 UDP 更安全”：安全与否主要看身份认证、加密及实现，不能仅按传输协议下结论。
- “443 端口一定是 HTTPS”：端口约定不是硬性规则。
- “证书报错时点击继续即可”：这是安全边界，应该先查设备时间、域名、证书链、代理拦截等原因。
- “ping 不通所以网页一定打不开”：ping 使用 ICMP，服务器可能专门忽略它。

## 自测

1. HTTP、TLS 和 TCP 分别承担什么工作？
2. 如果 `Test-NetConnection` 显示 TCP 443 成功，但浏览器报证书错误，问题在哪一层？
3. WireGuard 走 UDP，是否等于不可靠、不能安全传输？

**答案**：1）应用消息、安全通道、可靠字节流；2）优先检查 TLS/身份验证；3）否，WireGuard 使用自己的加密及会话机制。
